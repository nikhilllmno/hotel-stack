How Daisy Turns a Phone Call Into a Reservation

Daisy is an AI agent for hotels. A guest phones or texts in and books, changes, cancels, or checks a reservation through Daisy; hotel staff watch every conversation, booking, and payment from a web dashboard. Both worlds are served by one Node/TypeScript service — the repo confusingly named websocket-server, which is in fact plain REST/Express — the name is a leftover from an earlier OpenAI Realtime API (WebSocket-based) prototype that was replaced by Vapi but never renamed.

Daisy vs Danny. The agent is called Danny with a male voice and Daisy otherwise — same agent, same backend. The name is purely cosmetic; this page says "Daisy" to mean either.

The guest booking journey — read before write

A guest doesn't jump straight to a reservation. Daisy walks them through it, and each step is a separate /daisy tool call.

Step 1 · readWhat rooms do you have?GET /daisy/rooms — static room info, no availability/pricing
→
Step 2 · readAvailable? How much?GET /daisy/availability-lite — availability + pricing (also /room-type-rates)
→
Step 3 · writeBook itPOST /daisy/reservation → payment lifecycle below

Steps 1–2 are read-only — they create nothing. The reservation comes into existence only at step 3, and isn't confirmed until payment clears.

The action dispatch — one endpoint, four verbs

POST /daisy/reservation — switchReservationBasedOnAction()

GET fetch details
POST create
UPDATE modify dates / room
CANCEL cancel booking

Availability & pricing are read-only siblings: /daisy/availability-lite, /daisy/rooms, /daisy/room-type-rates. Multi-room bookings use /daisy/multi-reservation.

Reservation & payment lifecycle — how a booking becomes confirmed

A created reservation is not a confirmed one. The PMS write happens only after payment clears — not at creation.

Stripe · webhook-driven
  • Guest pays via a Stripe checkout link
  • Stripe fires a webhook on success / failure
  • Daisy reacts to the webhook to complete step 4
Shift4 · realtime, no webhook
  • Payment iframe embedded in our own site
  • We call Shift4 APIs in realtime to charge
  • Result returns on the API call — no webhook
Until step 6, the reservation exists only in Daisy and is not confirmed — it has not yet been written to the hotel's PMS.

The Hotel Dashboard → /api

Every property has its own dashboard account. Staff log in and see all the data Daisy generated for their hotel — calls, bookings, payments, escalations. It's pure REST over /api; despite the repo name there is no websocket to the browser (the SMS inbox simply polls).

How a dashboard account is bound to one property

A dashboard user is a User row with a role and a hotel_id. On login that hotel_id is baked into the JWT, and authMiddleware refuses any request where user.hotel_id ≠ token.hotel_id — so a hotel only ever sees its own data. SUPERADMIN is the exception and spans all properties.

Selected onboarded routes also accept an external Core JWT (SSO), validated against remote JWKS; the property is then resolved from the token's businessEnts claim. If Core auth fails, it falls back to the Daisy JWT.

04

PMS Webhooks & the Concierge Sibling (Alfred)

So far the PMS has been a destination we write to. It also calls back into us: every PMS except ResNexus supports webhooks, firing when something changes on their side.

PMS webhooks — who consumes them

  • Consumed mainly by alfred-core-svc (separate repo — see right)
  • Daisy also consumes them as needed
  • e.g. a reservation cancelled in Cloudbeds → Daisy is alerted → updates the status in its own DB so the two stay in sync

All providers except ResNexus support webhooks.

Alfred — post-reservation concierge (alfred-core-svc)

Alfred is primarily an AI concierge for the guest experience after a booking is made — a separate repo, and the primary consumer of the webhooks on the left. Guests chat with Alfred to:

requests
escalations
complaints
preferences
upsells early check-in · late check-out · property add-ons
DND requests

Alfred also sends scheduled messages to guests and collects feedback. Daisy = getting the booking made (pre-stay); Alfred = the stay itself (post-booking).

Property phone numbers

Each property has its own phone number, purchased or ported into Twilio. That number's inbound webhook routes a guest's call/text into Daisy (Section 1). So in the running system, a property = a hotel record + its dedicated Twilio number.

PMS coverage in dev

For each PMS (Cloudbeds, Stayntouch, Mews, Hostaway, ResNexus) we keep test properties in the dev environment, so every provider integration can be exercised end-to-end against dashboard.dev.dextr.ai without touching production.
